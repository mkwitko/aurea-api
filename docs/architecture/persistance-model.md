# AUREA Persistence Model

## 1. Purpose

This document defines the persistence model for AUREA.

It describes the canonical entities, relationships, identifiers, lifecycle states, ownership boundaries, and persistence rules required by the platform.

This document is intentionally independent from the ORM implementation.

The initial implementation is expected to use PostgreSQL with Prisma, but the persistence model represents the domain requirements rather than Prisma-specific syntax.

---

# 2. Persistence Principles

The persistence layer must follow these principles:

1. Business state is stored in PostgreSQL.
2. AI execution state is separated from business state.
3. Historical business decisions must remain traceable.
4. External provider IDs never replace AUREA IDs.
5. Multi-tenant boundaries must be enforced.
6. Important entities should use stable identifiers.
7. Soft deletion should be preferred for business entities when appropriate.
8. Historical records should not be silently overwritten.
9. Relationships should reflect business ownership.
10. Database constraints should enforce critical invariants whenever practical.

---

# 3. Identifier Strategy

All primary domain entities should use globally unique identifiers.

The initial implementation should prefer UUIDs.

Conceptually:

```text
Organization
  id: UUID

Workspace
  id: UUID

Business
  id: UUID

Goal
  id: UUID

Strategy
  id: UUID

Experiment
  id: UUID
```

Identifiers should be generated by the application or database using a consistent strategy.

Internal IDs must never depend on external provider IDs.

---

# 4. Tenant Hierarchy

The primary ownership hierarchy is:

```text
Organization
    │
    └── Workspace
          │
          ├── Business
          ├── ICP
          ├── Goal
          ├── Strategy
          ├── Experiment
          ├── Knowledge
          ├── Integration
          └── Agent Runs
```

Every business entity must be associated with a Workspace.

Every Workspace must belong to an Organization.

This creates the fundamental tenant isolation boundary.

# 6. Organization

Represents the top-level tenant.

Conceptual fields:

```text
Organization
├── id
├── name
├── slug
├── status
├── createdAt
├── updatedAt
└── deletedAt
```

### Rules

* `slug` must be unique.
* Organization deletion should be soft deletion initially.
* All workspace data must be isolated by organization.

---


### Rules

A Workspace cannot exist without an Organization.

# 37. Soft Deletion

Soft deletion should be used for:

* Organizations
* Workspaces
* Businesses
* ICPs
* Knowledge Documents

Core historical entities should generally not be deleted:

* Goals
* Strategies
* Experiments
* Outcomes
* Learnings
* Decisions
* Audit Logs

Historical records may instead be:

```text
ARCHIVED
CANCELLED
REJECTED
```

---

# 39. JSON Usage

JSON fields are allowed when:

* Data is provider-specific.
* Data is experimental.
* The structure is not yet stable.
* The data is primarily passed through to an external provider.

JSON should not be used to avoid modeling stable core domain concepts.

The following should remain strongly modeled:

```text
Goal
Strategy
Hypothesis
Experiment
Action
Outcome
Learning
Decision
```

---

# 40. Versioning

The following should support historical versions:

* Business Context
* Strategy
* Potentially ICP

The initial implementation should use explicit version records where historical reconstruction is required.

---

# 41. Database Constraints

Critical invariants should be enforced at the database level where possible.

Examples:

```text
Workspace.organizationId → required

Goal.workspaceId → required

Strategy.workspaceId → required

Hypothesis.strategyId → required

Experiment.hypothesisId → required

Outcome.workspaceId → required
```

Unique constraints should be added for:

* Organization slug
* Workspace slug within organization
* External references
* Provider identifiers where appropriate

# 44. Persistence Principle

The database should answer:

```text
What is true now?
```

The event system should answer:

```text
What happened?
```

The AI execution system should answer:

```text
How did the AI work?
```

The knowledge system should answer:

```text
What have we learned?
```

Together:

```text
Database
+
Events
+
AI Execution
+
Knowledge
=
AUREA Intelligence Infrastructure
```
